# Integration findings

## A second stdio client requires reconnection after the owner exits

- **Observed:** 2026-11-11 with Ahenk 0.3.0-beta.1, source revision `ad846f5`, on Intel macOS.
- **Reproduction:** Use the offline fixture configuration with a disposable Git repository. Initialize two Ahenk stdio processes against the same state directory. Call `list_capabilities` on each, close the first process, and call `list_capabilities` again on the second.
- **Observed result:** The first process reports `active`. The second lists the MCP tools but reports `state_busy`; `list_jobs` returns `STATE_BUSY`. The second process stays busy after the first exits. A fresh stdio connection then reports `active`.
- **Expected safety behavior:** A second process must never write to the state while the owner holds its lock. The client also needs a clear recovery action for an already-connected busy process.
- **Impact:** Two Codex sessions using one project MCP configuration can appear connected while only one can run jobs. Use one scheduler connection per state directory. Reconnect a busy session after the owner has exited.
- **Resolution:** The status response returns `next_action: "reconnect_after_owner_exits"`. The `STATE_BUSY` error gives the same recovery instruction.

## OpenCode session removal must precede the worker cleanup marker

- **Observed:** 2026-11-11 during private source policy review on revision `ad846f5`.
- **Impact:** A completed worker could publish its cleanup marker before its isolated session directory had been removed. A failed removal could leave session data behind while the attempt appeared clean.
- **Resolution in the working tree:** The cleanup marker is published after worker shutdown and successful session removal. A synthetic regression verifies that a removal failure keeps the marker absent and successful cleanup creates it.

## AGY session does not attest the executing account

- **Observed:** 2026-11-11 with signed AGY 1.5.4. The worker startup checks the model, agent, workspace and permission mode. It does not return an account principal that can be bound to a private source grant.
- **Impact:** A separate quota observation is insufficient to authorize a private source prompt. Ahenk rejects AGY private source grants and keeps the adapter on synthetic workloads. A scoped synthetic read completed live and returned the expected marker.
- **Resolution:** Private routes support `expected_account` and `expected_account_sha256` bindings in `private_source.routes`. When a route requires an attested account and the worker session does not attest one (such as AGY 1.5.4 Headless init), Ahenk blocks private dispatch with `ACCOUNT_ATTESTATION_REQUIRED` (or `ACCOUNT_MISMATCH` on principal mismatch) and `next_action: "use_attested_provider_or_keep_private_work_local"` without invoking the provider.

## OpenCode Free cooldown reached two synthetic routes

- **Observed:** 2026-11-11, with audited OpenCode 2.2.6. The native GLM route was still in its recorded cooldown. A separate stateless Beam synthetic read reached the upstream service and returned HTTP 429 with a retry boundary around 00:00 UTC.
- **Impact:** Keep both recorded cooldowns when reconnecting or creating a new local scheduler. No provider result was available for the Beam request.
- **Resolution:** Reuse the same state directory on reconnect. When migrating to a fresh state, `import-opencode-cooldown` carries both recorded and previously imported cooldowns, preserving their original attempt and retry deadline.


## Simulator processes do not inherit the simctl client's IP deny policy

- **Observed** on 2026-11-11 with Ahenk 0.3.0-beta.1 on Intel macOS 26.7.2 and iOS Simulator 26.5.
- **Reproduction** uses a standalone C socket probe compiled for the Mac and for the iOS Simulator. It makes one bounded TCP connection to a same-host listener and sends no payload. Run both probes against the same loopback listener, first without a policy and then with the following policy on the host probe or the `simctl` client.

```sh
policy='(version 1) (allow default) (deny network-outbound (remote ip))'
sandbox-exec -p "$policy" "$host_probe" "$loopback" "$port"
sandbox-exec -p "$policy" xcrun simctl spawn "$device" "$sim_probe" "$loopback" "$port"
```

- **Result** both controls connected. The restricted host probe returned `EPERM`. The Simulator probe still connected when the client was restricted. The policy parser rejected a numeric loopback address, and the `localhost` alias also allowed a connection to the host's own non-loopback listener.
- **Impact** the host policy is insufficient evidence of network containment for this Simulator spawn path. The experiment used synthetic data and only same-host connections.
- **Resolution:** The provider-free `local-test` runner stages digest-approved committed files. It applies the network policy inside the Simulator spawn before executing XCTest, and fails closed if the scoped probes cannot confirm it. See [local Swift and XCTest](local-swift.md).

## Codex coordinator adoption: observed probe and proposed rollout

- **Observed, 2026-11-11:** One main stdio MCP session successfully read five visible durable synthetic jobs: four completed OpenCode Free attempts and one `NOT_RUN`. A second isolated child session against the same state received `STATE_BUSY`. The records are route-agnostic and contain no metadata invocation counter. This probe demonstrates shared-state ownership and some successful synthetic dispatches; it does not measure the fraction of eligible work delegated, establish broad provider quality, or prove simultaneous client capacity.
- **Current beta boundary:** The installed 0.3.0-beta.1 evidence in today's probe supports bounded synthetic provider tasks. It does not establish installed-binary support for private-source grants, `trusted-local`, or `local-test`. The current checkout's docs and uncommitted source describe a private-source, digest-pinned, expiring, read-only OpenCode route and a provider-free local Swift test runner; treat these as working-tree evidence, not installed-beta capability or release qualification. The described private grant is not a checkout coding workflow. AGY remains synthetic-only because its session does not attest the executing account. OpenCode Free is tool-free; the `analysis` and `review` profiles disable provider filesystem tools. Where documented in the working tree, `trusted-local` writing is an explicit synthetic-only opt-in with host-user authority, so it is not a private-code isolation boundary. Free pricing, a loopback worker, a scoped snapshot, or a locally staged checkout does not by itself prevent provider egress or establish confidentiality. The described `local-test` command is deterministic tool orchestration for digest-pinned SwiftPM or standalone Simulator XCTest inputs; it does not provide local model inference, run app-hosted tests/UI tests/Xcode schemes, or constitute a provider job. See [private source policy](private-source-policy.md), [local Swift runner](local-swift.md), and [README](../README.md).
- **Proposed workflow map (synthetic-only today):**

| Work type | Route available now | Limitation before real-repository use |
| --- | --- | --- |
| Brief, story, or handoff review | Bounded `read_only` planning/research only when that exact role is qualified; use synthetic examples. | Real product briefs, backlogs, and handoffs are private inputs; no current zero-egress inference path. |
| Go implementation | In the current checkout, synthetic `trusted-local` patch is documented with explicit policy, one writer, and registered deterministic Go check; use only after verifying the installed binary exposes it. | Host-user authority; not a private-code boundary. |
| Swift implementation | Synthetic/read-only analysis; current checkout documents provider-free `local-test` for eligible digest-pinned tests; verify the binary before relying on it. | No local inference for writing; test command does not run Xcode schemes or app/UI tests. |
| Python/parser implementation | Synthetic/read-only analysis only. | No documented Ahenk-local Python writer/test route is established by the installed beta. |
| Independent technical review | Synthetic patch review through a distinct provider family and hash-verified diff handoff, where route quality and policy admit it. | Provider-family separation is not an OS boundary; the review prompt still discloses its diff to that provider. |
| Domain, security, or UI review | Synthetic examples can calibrate general roles; keep specialist judgment and acceptance with the responsible reviewer. | General role calibration does not grant financial, security, or visual expertise; actual private diff/screenshot disclosure and same-state UI evidence are not provided by the current route. |
| Unit/API/SQL/fixture tests | Registered synthetic Go check is documented in the current checkout; provider-free SwiftPM tests are documented for approved manifests. | Installed-binary support is unverified here. No general API/SQL integration or private-fixture execution is implied. Keep database and service test ownership local until a reviewed runner exists. |
| Native Xcode scheme, app-hosted, or Simulator UI acceptance | No installed-beta route is evidenced. | Keep one local Xcode/Simulator runner; local standalone XCTest is narrower and is not a substitute. |
| Coordination, dependency ordering, locks | Synthetic `delegate_batch` / decomposition with one Ahenk state owner; a single session can schedule eligible tasks. | Do not fan out clients sharing one state. Native provider child work is experimental and must not be assumed. |

- **Proposed adoption sequence:** (1) Make daily use measurable before widening scope: for each eligible task, retain a sanitized coordinator ledger row with request/job IDs, category, eligibility decision, routed/not-routed reason, and terminal outcome. `list_jobs` is not an invocation counter. (2) Route bounded synthetic brief/story maintenance, read-only research, and role-qualified architecture/planning/reasoning tasks through one persistent stdio owner. Check `list_capabilities(include_quota: true)` and scoped routing preview before dispatch; require fresh, matched role-quality, capacity, cost, and privacy evidence. (3) Verify the installed binary and local policy before attempting synthetic checked Go patches or provider-distinct artifact review; the current checkout's docs/tests are not proof of installed capability. Keep one shared-file writer and one API/SQL/Simulator runner. (4) For actual private-repository work with zero private egress, do not send code, diffs, briefs, logs, or screenshots to an external model. Ahenk needs a separately verified local inference route plus an OS-enforced file/network boundary and local deterministic checks before it can do that work; none is established by the installed beta. Until then, keep implementation and specialist review local to the authorized environment. A private read using the checkout's documented exact grant is an external disclosure and therefore does not meet a zero-egress requirement. (5) Treat native Xcode/UI acceptance as a local coordinator-owned gate until a separate, tested runner supports schemes, app hosting, UI evidence capture, cleanup, and network enforcement.
- **Concrete workflow examples:** For Yarınlık, TASK-053's Plan-day work can use Ahenk today only for a synthetic acceptance/architecture analogue; the real native edit and cancel flow stays in the authorized local checkout, with its owned synthetic PostgreSQL and Simulator acceptance run by their assigned local owners. TASK-162's BUY/SELL lot and cost change needs the local financial implementation and independent domain review; a synthetic explanation or role fixture does not validate financial semantics, and actual diffs must not be sent to an external reviewer under a zero-egress requirement. BMAD/Superpowers planning, TASK-catalog mapping, and handoff maintenance can be delegated as bounded synthetic examples; real planning artifacts remain local until a verified zero-egress inference path exists. These examples show useful day-to-day synthetic delegation without treating external inference as private-repository access.
- **Evidence to record per task:** Keep a synthetic `request_id`, parent and child job IDs, task class, data class, acceptance IDs, allowed paths, selected route and route evidence, quality tier/source, capacity warnings, cost evidence, terminal status, artifact/diff hash, deterministic-check status, reviewer provider family and verdict, and coordinator acceptance. Record `BLOCKED` or `NOT_RUN` when an admission gate or local capability prevents dispatch; do not count a planned task as a provider invocation. The current job listing has no invocation counter, so measure adoption from an explicit coordinator task ledger that links eligible tasks to job IDs, not from `list_jobs` totals alone.
- **Proposed acceptance checks:** In a disposable synthetic repo, verify one `read_only` task produces its exact marker and a traceable terminal job; an expired/unapproved private grant and an unqualified role are blocked before dispatch; a zero-price route still fails closed on cost or privacy policy; stale/unknown quota is not treated as available capacity; a synthetic patch is applied only as a verified artifact, passes its registered deterministic check, and receives a distinct-provider review bound to the same diff hash; a second stdio process cannot access the owner's state and a fresh connection works after owner exit; duplicate requests are counted once in the coordinator ledger; and a Simulator test attempt that cannot establish the inner network boundary reports `NOT_RUN`. Before any local-inference/private-work expansion, separately prove that an unapproved file, prompt, diff, log, or screenshot cannot cross the process boundary, and that an approved local implementation can pass its named check without network access or writes to the source checkout. Keep live provider availability checks separately labeled, opt-in, synthetic, and bounded; they are not substitutes for offline contract tests or repository acceptance.
- **Resolution:** `list_capabilities` now reports `version`, `binary_sha256`, `local_runners` (`swiftpm`, `simulator-xctest`, and `xcode-scheme`), and per-repository `repo_admission` with explicit unmet gates and `next_action` guidance. Coordinators can preflight exact binary identity, private-source admission, and local runner boundaries from the single owning stdio session before any dispatch.

## Per-assignment Ahenk preflight and TASK-053 decision

- **Procedure (proposed):** Before assigning each task or subtask, use the existing Ahenk stdio owner (never a second connection to the same state) to inspect `list_capabilities(include_quota: true)` for the registered synthetic scope and check the exact task class, quality evidence, provider/data policy, cost, quota, tools, and review requirements. Choose a bounded synthetic-only candidate when one matches the work; dispatch only after all gates pass. For private-repository work, never send real source, brief, diff, test log, or screenshot to a provider as a “probe.” If no eligible route exists, record `BLOCKED` or `NOT_RUN`, the expected route, observed gate, impact, version/fingerprint evidence (or `NOT_RECORDED`), and the next condition that would justify rechecking; proceed with the separately authorized local owner when available. Do not invent a job ID or count a capability check as an invocation. Reuse an existing finding when the expected and observed behavior, route/version, and impact match; append a new dated entry only for materially new evidence. A missing route is a capability boundary until a reproducible contract violation establishes a product bug.
- **Observed decision, 2026-11-11 — TASK-053:** The expected safe candidate was a synthetic, bounded, read-only planning/analysis task if role-qualified; the actual native edit/cancel behavior and owned synthetic PostgreSQL/Simulator acceptance needed local execution. A fresh `list_capabilities` result on the registered synthetic scope showed an active scheduler, OpenCode `tool_free` synthetic `read_only`, and AGY Headless synthetic preflight. Implementation was disabled because writer isolation was unverified. No private checkout, native Xcode, or Simulator role was available. The capability response did not include a version/build fingerprint (`NOT_RECORDED` here). The coordinator therefore made no Ahenk dispatch and used the authorized local Codex Xcode-only runner after this check.
- **Impact:** TASK-053 local acceptance could proceed without disclosing private work or claiming a provider job. Ahenk remained available for a separately scoped, role-qualified synthetic read-only analogue; that would not establish the native edit/cancel or database/Simulator acceptance.
- **Recheck trigger:** Repeat the capability check on each assignment. Reconsider Ahenk for a native implementation only after the installed binary exposes the required role, writer isolation is verified, and a no-egress boundary plus deterministic local check is evidenced. Reconsider a separate Simulator/Xcode assignment only after that runner is explicitly exposed and its app/scheme, UI evidence, cleanup, and network gates are verified. Until then, route these steps to their authorized local owners. This is a recorded eligibility decision, not a claim that the current missing roles are product defects.
- **Resolution:** `list_capabilities` now includes `version`, `binary_sha256`, and `local_runners` on every response (including `state_busy` responses for version/fingerprint), and `xcode-scheme` is explicitly reported as `unavailable` with `reason: "XCODE_SCHEME_RUNNER_UNVERIFIED"` and `next_action: "route_xcode_scheme_and_ui_acceptance_to_authorized_local_owner"` unless a verified local Xcode scheme runner is configured.

## Product defect: owner-approved Yarınlık work cannot reach an actual Ahenk route

- **Observed, 2026-11-11:** The owner explicitly authorized sending scoped private Yarınlık repository content for actual work delegation. The installed Ahenk capability lookup for repository ID `yarinlik` returned `repository is not registered`. The available installed AGY route was registered only for synthetic work: its preflight allowed analysis, while implementation was disabled with `WRITER_ISOLATION_UNVERIFIED`. Separately, the upstream working-tree `private-source-policy.md` states that AGY remains synthetic-only because its worker does not attest the executing account; this is working-tree policy evidence, not proof of the installed binary's policy. One synthetic `gemini-3.8-flash-medium` reasoning job completed in one attempt (31.533 seconds), with `SCOPED_CONTEXT`, `PROCESS_EXIT`, `AGY_PROFILE_VERIFIED`, and `DOCUMENTED_COST_PROTECTION`; no private Yarınlık job was dispatched and no private bytes were sent. The user reports that Codex quota was exhausted. Ahenk quota was unmatched (`UNKNOWN`), so this evidence does not quantify how much delegation would have changed Codex usage.
- **Expected:** An explicit owner grant for a named private repository should make an eligible, bounded task routable after Ahenk verifies the source scope, consent, account identity, data handling, route, cost, and execution boundary. If those checks cannot pass, the capability response should identify the precise unmet gate and supported next action; owner authorization alone must not silently imply that an unavailable route exists.
- **Impact:** Even with owner approval, the installed Ahenk capabilities could perform only a synthetic analogue, not the requested real-repository work. This left the actual task with Codex and is the reported context for Codex quota exhaustion; the exact quota impact is not independently measured.
- **Remediation:** Add a deliberate private-work admission path that requires explicit scope and consent, verified AGY account attestation, exact approved paths and content digests, expiry, and a data-handling review that excludes secrets and personal data. Enforce a reliable cost gate. Keep implementation disabled until writer isolation is verified; then require a hash-verified patch, named deterministic checks, and independent review bound to the same patch. Report local Xcode execution as a separate capability, not as part of provider delegation. Do not bypass these gates or relabel private inputs as synthetic.
- **Acceptance conditions:** In disposable test repositories, (1) owner consent plus a verified account and complete scoped grant admits only the approved task and exact pinned files; (2) missing consent, wrong/unattested account, unregistered repository, unapproved path, changed digest, expired grant, secret/personal-data classification, or unknown cost/capacity each blocks before provider dispatch and identifies the gate; and (3) write admission remains blocked until writer isolation is verified. If a write route produces a patch, integrating it requires a verified patch hash, passing named registered local checks, and independent review bound to that same hash. A read-only private task returns an auditable result tied to the grant and snapshot; and (4) local Xcode execution is advertised only when a separately verified local runner supports the requested scheme and acceptance mode. Verify negative cases produce no provider invocation and no out-of-scope file access.
- **Resolution:** Implemented and verified in `internal/model/private_source.go`, `internal/execution/snapshot.go`, `internal/readiness/local_runners.go`, `internal/orchestration/{engine,implementation,review,capacity}.go`, `internal/mcpserver/server.go`, and `cmd/ahenk/main_test.go` (`TestPrivateWorkAdmissionAndLocalRunners`):
  1. Unregistered repository queries (`list_capabilities` and `delegate_task`) return `code: "REPO_NOT_REGISTERED"`, `gate: "REPO_NOT_REGISTERED"`, and `next_action: "register_repository_in_config"`.
  2. `PrivateSourcePolicy` enforces `owner_consent`, `expires_at`, exact `files` SHA-256 digests from `HEAD`, `approved_brief_sha256`, secret and personal-data classification gates (`SECRET_DETECTED`, `PERSONAL_DATA_CLASSIFIED`), and route-level `expected_account` / `expected_account_sha256` attestation (`ACCOUNT_ATTESTATION_REQUIRED`, `ACCOUNT_MISMATCH`).
  3. Private write admission remains blocked with `WRITER_ISOLATION_UNVERIFIED` unless `writer_isolation_verified: true`, `allow_write: true`, `require_independent_review: true`, and registered `go_checks` are configured; when enabled in a `distinct_provider` batch, Ahenk executes the patch in an isolated detached worktree, runs the registered deterministic Go check, binds the independent review verdict to the exact `artifact_sha256` and `"PASSED"` check status, and records `grant_digest`, `snapshot_id`, and `PRIVATE_GRANT_BOUND` on the result without mutating the source checkout.
  4. `list_capabilities` reports `local_runners` separately from provider delegation and advertises `xcode-scheme` as `available` only when `local_xcode_runner.verified` and `schemes` are configured.
